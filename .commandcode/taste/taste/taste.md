# Taste
- Prefers validation error messages to be absolutely positioned (out-of-flow) with reserved bottom padding/spacing on each field, so a message appearing or clearing never reflows the field or shifts sibling columns and grid rows; accommodates the reserved space (including shrinking the message font size ~10%) rather than relying on in-flow relative positioning. Confidence: 0.8
- Maintains numbered markdown design specs in the repo root (e.g. `overview.md`, `01-data-model.md`, `06-express-app-structure.md`) that act as the source of truth; implementation should follow the specs precisely rather than improvise. Confidence: 0.9
- Prefers each working session to target one specific spec doc at a time ("At this session I need us to implement @06-...", "can we proceed with the frontend implementation as well?" after adding @03-...), with referenced docs consulted first for context before writing code. Confidence: 0.9
- Values a local-first development workflow: explicitly wants to run the local server and test the frontend locally, and expects setup/run/test steps to be documented and workable (e.g., API base URLs should be configurable to point at a local server rather than hardcoded to production). Confidence: 0.8
- Wants realistic mock/seed data during development so the full flow is exercisable end-to-end without live production dependencies: seeded listings in the local DB (e.g., a Prisma seed script) AND mocked external endpoints that aren't implemented yet (asked for mock data for the not-yet-built WordPress availability/reservation endpoints when using the test URLs). Confidence: 0.9
- Prefers database migration tooling to never auto-create the database: wants Prisma configured so `migrate dev` (which creates the DB and requires a shadow DB) is replaced by a `migrate deploy` workflow that only applies migrations to an already-provisioned database, with migration files generated via `--create-only`. Confidence: 0.8
- Prefers mock modes for not-yet-implemented external services to be toggled by an env flag (e.g., `WP_MOCK_MODE=true`) rather than code changes, with the mock kept in a separate module, mirroring the real client's response/error shapes so error handling behaves identically in both modes. Confidence: 0.6
- Keeps the server's strict Content Security Policy (helmet's defaults) intact: pages must avoid inline `<script>` blocks (e.g., set runtime config from an external bundle's module code) rather than loosening CSP with `'unsafe-inline'`, hashes, or nonces. When CSP blocks legitimate content (e.g., an external `img-src` for a listing logo), the fix is the minimum-scoped allowlist (adding the specific allowed host, such as `config.wpBaseUrl` to `img-src`) rather than broad loosening to `*`, `https:`, or `data:`. Browser CSP violations are reported as real errors to fix. Confidence: 0.7
- Reports bugs by pasting the exact error output (e.g., a verbatim browser console message like "Uncaught SyntaxError: Cannot use import statement outside a module" or "Error: intlTelInput.utils is required for getNumber()") with minimal framing, expecting the agent to diagnose the root cause and fix it directly. This also extends to styling bugs, reported at the CSS selector/class level (e.g., "rdp-month_grid is available, however rdp-weekday no. this is the current selector for the date cells fsb-rdp-day") rather than vague visual descriptions. Confidence: 0.9
- Runs the backend dev server in watch mode (`node --watch src/server.js`) for auto-restart on file changes, rather than relying on a manually restarted or background process. Confidence: 0.7
- Expects the dev environment to be left in a clean, self-startable state after a session: background servers the agent left running occupy the port and block the user's own dev-server start, which the user reports as a problem to fix. Confidence: 0.6
- Prefers scoping UI work to a single component per session: asks to analyze the rest of the project for context but explicitly focus on that one component (e.g., "analyze the rest of this project and we will focus on this component" when pointing at a widget's ReservationForm.jsx). Confidence: 0.6
- Prefers an incremental, staged approach to UI work: treats audit/checkup findings as a backlog to address "at a later stage" rather than applying them immediately, and instead works on one specific aspect of the UI at a time (e.g., rearranging the input fields' layout for the desktop version). This staged, one-thing-at-a-time approach also governs moving between parts of the project: once a stage is accepted ("For the moment the ui is ok"), the user shifts to the next module (e.g., @api.js) rather than continuing to polish. Confidence: 0.8
- Asks the agent to analyze and explain what a specific file/module does before any edits are made ("can you help me determine what is happening here?" on @api.js), expecting a walkthrough of the code's design plus surfaced bugs/risks, and leaving the decision to fix to a follow-up question. Confidence: 0.6
- Wants explanations of how a function/request works end-to-end across the whole stack (widget → Express BFF → external service), traced in terms of actual runtime behavior governed by env config and running-server state (e.g., whether `WP_MOCK_MODE` makes `getAvailability` hit WordPress or the in-memory mock) — asked "can you explain how getAvailability works at the moment? I would expect that it would reach the wordpress website", with the expectation/discrepancy itself part of what needs explaining. Confidence: 0.5
- Specifies exact desktop form layouts by dictating the row grouping of fields rather than leaving arrangement to the agent: booking details (date/time/guests) as one 3-column row, contact fields (first/last name, email/phone) as 2-column pairs, and free-text fields like a comments textarea spanning full width — while the narrow/mobile layout stays stacked. Confidence: 0.6
- Considers an optional comments/notes textarea (full-width, with a character cap and live remaining-characters hint) a standard part of a booking/reservation form. Confidence: 0.5
- Wants a watch-based dev loop for the frontend: explicitly asked how to have Vite recompile on file changes (rather than running a separate dev server or manually rebuilding after each edit), and prefers the built output served by the existing Express static setup. Confidence: 0.6
- Prefers using a mature third-party library for complex form controls over keeping a hand-rolled or native control: explicitly asked to install `intl-tel-input` for the phone field (which previously used a custom country-code dropdown + manual libphonenumber validation), and agreed to replace the native date input with react-day-picker after a recommendation. Confidence: 0.7
- When a bug surfaces in a hand-rolled integration, suggests switching to a library's official wrapper/React version as the first instinct (e.g., "Perhaps we could switch in using the react version of intl-tel"), expecting the agent to evaluate the option and explain if no wrapper exists. Confidence: 0.5
- Prefers to skip automated browser verification (headless Chromium/DOM dumps) and instead have the agent summarize what changed; the user will test in their own browser and the two will debug together only if the user detects an issue ("Skip browser verification. We will debug together if I detect an issue"). Confidence: 0.6
- Asks the agent for library recommendations and expects a tradeoff analysis (fit with the widget's constraints, a11y, i18n, bundle size, custom-code cost) before committing to a new dependency, rather than adopting the first candidate ("Do you have any library recommendations for a datepicker?"). Confidence: 0.5
- Wants European date conventions in the widget UI: the date field should display and enter dates in d/m/y format (e.g. `24/12/2026`, placeholder `dd/mm/yyyy`) — explicitly requested "european date format d/m/y" when replacing the native date input. Confidence: 0.8
- When reporting a regression, states the symptom at a high level ("I get an error now when submitting") without pasting a stack trace, and expects the agent to reproduce it independently via live end-to-end testing across the full stack (hitting the running BFF, then middleware/auth/config/DB as needed), root-cause it, and verify the fix against the actually-served bundle (curl the built artifact) rather than relying on source edits or build logs alone. Confidence: 0.6
- Expects third-party UI components (e.g., the react-day-picker calendar) to be styleable/themed to match the widget's design system rather than left with library defaults — explicitly asked whether styling the datepicker itself is possible. Confidence: 0.5
- Is skeptical of claims that a library's bare CSS import (e.g. `import 'react-day-picker/style.css'`) actually applies styles; when styling appears missing, expects the agent to verify against the real built/served CSS (confirming the library's selectors survived bundling/minification) rather than trusting the import statement or source files alone. Confidence: 0.5
- Prefers flag icons over text/string labels in the language selector UI (explicitly requested "use a flag icon instead of a string label" when adding multi-language support), with the active language still clearly indicated. Confidence: 0.7
- Points the agent to existing image assets already in the repo (e.g. `@widget/src/assets/`) for UI icons/flags rather than having the agent source or create new ones. Confidence: 0.5
- Prefers the language selector to be a compact custom select/dropdown (single trigger showing the current language's flag + name, opening a menu of the options) rather than a grid/row of buttons showing all options at once — explicitly rejected the flag-button row: "I don't want them to be displayed in a grid. I prefer a custom select element for this." Confidence: 0.8
- When an external-service API contract changes (e.g. the WordPress availability endpoint now takes a single `date` param instead of `from`/`to`), expects the change threaded through the whole stack consistently — the client, its calling route, the mock implementation, and the test stubs/assertions all updated together so every layer's signature and the test suite stay in sync. Confidence: 0.8
- Treats the upstream external plugin (WordPress) as authoritative over what data the BFF must forward: objected to the agent stripping `public_id` from the reservation payload, arguing the plugin cannot match the reservation to a listing without it, and expects the BFF to forward the widget payload as-is (including routing keys) rather than the agent assuming a field is "routing-only" and safe to drop. Confidence: 0.8
- Expects client-side components to consume the WordPress/API snake_case data shape as-is (e.g. `arrival_date`, `first_name`) rather than the widget inventing its own camelCase view model: explicitly directed "fix success.jsx to consume the snake_case payload", and prefers rendering the server's created-reservation response (authoritative WP data) over a locally-built draft payload. Confidence: 0.8
- Wants backend data model additions (e.g. a new WordPress listing field such as `blocked_dates`) propagated through the full stack — cache/DB schema, sync route, API response, and frontend component — so the new data is consumable in the UI. Confidence: 0.7
- When a UI feature is removed (e.g. the reservation form's title heading), expects a thorough cleanup of the now-dead supporting code rather than a minimal markup cut: removes the unused CSS rules and the now-unused `form.title` i18n key from ALL locale files (en/el/de/it/fr) so the bundle stays lean and no dead references linger. Confidence: 0.5
- Prefers to be guided with explanations and procedures rather than having the agent perform actions directly — explicitly stated "guide me not perform it," so during debugging the agent should walk through the steps/env setup instead of executing commands on the user's behalf. Confidence: 0.9
- Prefers non-minified, debuggable builds with source maps so errors are traceable to real source files and line numbers, rather than chasing minified walls or React error codes — wants the Vite dev server (unminified by default) and also `vite build --mode development` / `minify:false` + `sourcemap:true` available for debugging the production bundle served into the shadow DOM. Confidence: 0.85
- Uses a Vite dev-server proxy (e.g. `/api` → BFF origin) to keep the widget and API on a same-origin-aligned workflow during local debugging, rather than relying on runtime `window.FINDSPOT_API_BASE` config — part of the documented local dev setup so stack traces and network calls line up with the running BFF. Confidence: 0.6
- Deep-links a real listing on the Vite dev server (`localhost:5173`) via a `?id=<publicId>` query parameter read by a dev `index.html` that sets `data-public-id` on the root element, rather than path-based `/<publicId>` — because Vite only serves the declared build entries and has no BFF-style `/:publicId` catch-all, so attaching a listing id in the path 404s. Confidence: 0.65
- Allow-lists dev origins on the BFF (e.g. `localhost:5173`) via the `EXTRA_ALLOWED_ORIGINS` env flag during local debugging, rather than persisting them into the listing's WP-synced `allowed_domains` (which are locked to `localhost:3001` from WordPress). Confidence: 0.65
